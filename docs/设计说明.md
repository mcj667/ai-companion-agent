## 核心设计

### 1. Advisor 链

Spring AI 的 `Advisor` 相当于"环绕通知"，在请求前后自动插入逻辑。项目里挂了三个：

| Advisor | 顺序 | 挂在哪 | 干什么 |
|---|---|---|---|
| `MessageChatMemoryAdvisor` | 0 | 全局 | 请求前把历史塞进 Prompt，响应后把这一轮存进 Redis |
| `MyLoggerAdvisor` | 10 | 全局 | 打印请求/响应日志 |
| `QuestionAnswerAdvisor` | 0（默认） | **只挂 `/rag`** | 检索向量库，把相关文档拼进 Prompt |

**顺序规则：数字越大越靠近模型。**

### 2. 对话记忆（给模型用的）

```
用户提问
   │
   ├─ MessageChatMemoryAdvisor.before()
   │     └─ redisChatMemory.get(chatId)      ← 读历史
   │     └─ 拼进 Prompt
   │
   ├─ 调 DeepSeek，拿回复
   │
   └─ MessageChatMemoryAdvisor.after()
         └─ redisChatMemory.add(chatId, 新消息) ← 写历史
```

关键点：**这是给模型用的上下文，不是给前端的接口。** 数据只流向模型，不流向浏览器。

Redis 里存的是 Kryo 二进制，比 JSON 体积小，但**不能用 `redis-cli` 直接看懂内容**。

### 3. 会话历史（给前端看的）

前端要显示气泡和左侧列表，靠的是另外三个 REST 接口。**同一份 Redis 数据，换了个出口。**

```
GET /love/sessions  →  读 chat:sessions  →  左侧列表
GET /love/history   →  读 chat:memory:*  →  中间气泡
```

**这里有个坑**：`ChatMemory` 接口只提供 `add/get/clear`，**没有"列出所有会话"的能力**。原因是它的 key 是 `chat:memory:{chatId}`——不知道 chatId 就取不出来。所以另外用一个 Redis ZSet 维护会话名单。

> 也没用 `KEYS chat:memory:*` 去扫。`KEYS` 会阻塞整个 Redis，生产环境是禁用命令。

**这里还有第二个坑**：气泡上那个「知识库问答 / 普通对话」的标签，**对话记忆里根本没有**。
模式只体现在「你调了哪个接口」（`/love/rag` 还是 `/love/chat`），而往 Redis 写记忆的
`MessageChatMemoryAdvisor` 挂在 `ChatClient` 上，它只知道消息内容、不知道 URL。
所以这份信息得在控制器另外采一次（`LoveController` 里 `chatModeRegistry.record(...)`），
存进 `chat:modes:{chatId}`。

读的时候也**不能按下标硬对**：消息按**条数**裁剪（只留 20 条），模式按**轮数**裁剪，
两边规则不一样，窗口一满就整体错位。解法是**从最新的那条往前对**——每遇到一条 AI 回复就
消费一个模式，用户消息跟它后面那条回复算同一轮。因为两边都是「砍掉最老的」，
从后往前数一定准；就算中间真错了一轮，也只影响更老的那几条，新的永远是对的。

> 这个对齐算法单独写了单元测试钉住（`ChatHistoryServiceTest`），因为算错一位不会报错，
> 只会安静地把标签整体串一格，肉眼很难发现。

### 4. RAG 检索增强

```
用户提问
   │
   ├─ QuestionAnswerAdvisor.before()
   │     ├─ 调百炼把"问题"向量化        ← 每次提问都要调，依赖网络
   │     ├─ 去 SimpleVectorStore 找最相关的 4 段
   │     └─ 拼进 Prompt（"只能根据以下内容回答"）
   │
   └─ 调 DeepSeek，拿回复
```

**注意**：向量化走的是百炼，对话走的是 DeepSeek。所以 RAG 比普通对话多一次网络请求。

知识库在 `src/main/resources/document/`，用 `MarkdownDocumentReader` 按水平分割线切段。

> `QuestionAnswerAdvisor` 在 Spring AI 1.1.8 里**没有"检索结果为空"的兜底**。如果向量库是空的，默认模板会让模型回答"我无法从已知信息中回答"，看起来像模型变笨了，其实是没检索到东西。

**默认模板还有个坑（已修）**：它只把**最相似的 4 段**正文丢给模型（`topK` 默认 4，知识库一共 15 段），
却**不告诉模型这堆文字是什么**。所以用户一问"你知道《某文档》吗"，模型手上只有 4 段、
又不知道这只是片段，只能回"我没有这份文档"——听起来像功能坏了，其实它在如实回答。

现在换成了自定义模板 `prompts.RAG_ANSWER`，在 `LoveAppVectorStoreConfig` 里用
`promptTemplate(...)` 挂上去，把话说清楚：这是「知识库里找到的相关内容」、不一定是全文，
能答就直接答、问到某份文档就把看到的内容讲出来。

> 占位符 `{question_answer_context}` 是 Spring AI 的固定约定，而模板渲染是**严格模式**——
> 写错一个字母不是"提示词变差"，而是**每次 RAG 提问都直接抛异常**。
> 所以单独写了 `RagPromptTemplateTest` 钉住它。

### 5. 工具调用（联网搜索）

**先纠正一个最常见的误解：模型不执行任何代码。**

它只会"说"一句：「我要调 `webSearch`，参数是 `{"query":"杭州天气"}」。
真正发 HTTP 请求的是**我们本地的 Java 方法**，返回的文本再被塞回对话里，模型才接着写答案。

```
用户："杭州今天天气怎么样？"
   │
   ├─ 第 1 次调模型
   │     └─ 模型不写正文，只说"调 webSearch，query=杭州天气"
   │
   ├─ Spring AI 反射调用 WebSearchTool.webSearch("杭州天气")   ← 我们写的代码在跑
   │     └─ 调博查接口，拿到 5 条结果
   │
   ├─ 把搜索结果当成一条"工具消息"塞回对话
   │
   └─ 第 2 次调模型
         └─ 模型这次才写出正文答案
```

所以**一轮工具调用 = 至少两次模型调用**，这就是它比普通对话更慢、更贵的原因。
后端日志里那两条 `AI Response` 就是直接证据——第一条是 `text="<none>"`，只有工具调用、没有正文。

两个工具：

| 工具 | 干什么 | 依赖 |
|---|---|---|
| `WebSearchTool.webSearch` | 调博查搜索，返回 5 条结果的标题 + 链接 + 摘要 | 博查 BochaAI（国内直连） |
| `WebPageTool.fetchWebPage` | 抓一个 URL 的正文，HTML 转纯文本后截断到 3000 字 | jsoup |

用的是 Spring AI 1.1.8 的 `@Tool` 注解 + `.tools(Object...)`。
**老教程里那套 `functions(...)` API 在 1.x 里已经删掉了**，照着旧文章写会编译不过。

**几个刻意的设计：**

- **`@Tool` 的 description 是写给模型看的说明书，不是写给人看的注释。** 模型完全靠这段话判断"什么时候该调"，写含糊了就会该调不调、或者乱调。这是工具调用里最影响效果、也最容易被面试追问的一环。
- **工具方法绝不抛异常。** 工具是模型在运行时决定要不要调的，我们没法在外面包一层 try/catch——一旦异常抛出去，整个对话请求就 500 了，用户什么都看不到。所以超时、401、JSON 解析失败一律返回一句人话，等于把"失败了"也当成一条工具结果交给模型，模型能顺势跟用户解释。具体原因只写进日志。
- **工具按请求挂，不做成 `defaultTools`。** 做成默认的，另外四个模式也会全带上工具，每次闲聊都要多花一次模型判断的钱，而且演示时看不出"用了工具"和"没用工具"的区别。这也跟 RAG 的挂法一致（`doChatWithRag` 里那个 `.advisors(questionAnswerAdvisor)`）。
- **抓取前必须删掉 `script` / `style`。** `Jsoup.text()` 会把标签里的内容也当正文，不删的话页面的 JS 源码会整段灌进模型上下文，既烧 token 又干扰回答。
- **工具方法返回 `String` 会被 JSON 序列化**（Spring AI 的默认结果转换器），所以模型看到的其实是带引号的 `"..."`。对纯文本无害，但知道这件事能解释一些奇怪的观察。

**工具消息会顺带污染两个地方，已经处理掉了：**

加了工具调用之后，一轮里会多出两条消息——「我要调工具」那条 assistant（只有 toolCalls、**没有正文**）
和「工具返回结果」那条 `TOOL`。它们会踩两个坑：

1. **模式标签整体错位**：`resolveModes()` 原本是"每遇到一条 assistant 就消费一个模式"，而模式列表每轮只记一个。一轮出现两条 assistant 就会多吃一个，**从那一轮起后面全部串一格**——跟当初把 `mode` 写死成 `"chat"` 是同一类 bug。现在只让**有正文的** assistant 计数。
2. **搜索结果变成一个巨大的气泡**：`TOOL` 消息的正文是几千字搜索结果，而 role 会被判成 `assistant`，看着像 AI 说了这么一坨。现在 `listMessages()` 直接跳过 `TOOL` 类型。

> 这两条防线各只有一行代码，但都单独写了测试钉住（`ChatHistoryServiceTest`）——
> 因为它们出错时**不报错、不崩溃**，只是安静地显示错的东西，肉眼很难发现。

### 6. MCP 接入（工具来自进程外部）

第 5 节的工具是**我们自己写的 Java 方法**。MCP 是另一回事：工具由**一个独立的进程**提供，本项目里根本没有这些方法的代码。

```
应用启动
   │
   ├─ 拉起 MCP server 子进程（这里配的是 npx @amap/amap-maps-mcp-server）
   ├─ 握手，问它："你有哪些工具？"
   └─ 对方把工具清单报回来 → 包成 ToolCallbackProvider → 注入进 LoveApp
```

调用写法和普通工具调用几乎一样，差别只在工具**从哪来**：

| | `/love/search` | `/love/mcp` |
|---|---|---|
| 代码 | `.tools(webSearchTool, webPageTool)` | `.toolCallbacks(toolCallbackProvider)` |
| 工具从哪来 | 本项目里的 `@Tool` 方法 | 一个独立的 MCP 服务进程 |
| 模型看到的 | 一张工具清单 | 一张工具清单（没区别） |
| 加新工具要改 Java 吗 | 要 | **不用**，改 `mcp-servers.json` 就行 |

**代价是启动期强耦合。** MCP server 是在**应用启动时**就连的，连不上会这样：

```
loveApp → deepSeekChatModel → toolCallingManager → toolCallbackResolver
       → mcpToolCallbacks → mcpSyncClients → Client failed to initialize
```

整条依赖链断在最后一个 bean 上，**整个 Spring 容器起不来**。也就是说 MCP server 挂了 ≠ "MCP 这个模式用不了"，而是**整个项目打不开**。

这跟第 5 节那种"工具失败了就返回一句人话"完全不是一个量级——因为那些是本地方法（失败只影响那个工具），而 MCP 是**外部进程**（失败拖垮启动）。这也是"为什么不全用本地工具"最好的答案。

配置里那行 `initialized` 就是给这种情况兜底的：

```yaml
spring:
  ai:
    mcp:
      client:
        initialized: true      # 启动时就去连 MCP server
        stdio:
          servers-configuration: classpath:mcp-servers.json
```

- `true`（**默认值**）：启动时就连，MCP 工具真正可用
- `false`：bean 照常建好、但启动时先不连。应用**一定**能启动，代价是 MCP 工具为**空**（`/love/mcp` 退化成一次普通对话）

**这个项目是怎么让 `true` 成立的**：`npx -y @amap/amap-maps-mcp-server` 每次都要联网下包，
而这台机器到 npm registry 时通时不通，应用启动就会失败。后来用
`npm i -g @amap/amap-maps-mcp-server` 把包装到了本地，`npx` 不用再联网就找得到它，`true` 才成立。

> 所以换机器 / 包被删 / 网络又抽的时候，这里会**重新变成"应用起不来"**。
> 认得出这个现象、并把 `initialized` 临时改回 `false` 让应用先活过来，就是这条排错路径的价值。
> 详见[已知限制与排查](已知限制与排查.md) → 应用启动直接失败。

**实测确认真的接上了**（不只是"看起来配对了"）：启动日志里出现
`Amap Maps MCP Server running on stdio` 和 `Server response with Protocol: 2024-11-05 …
Info: Implementation[name=mcp-server/amap-maps]`，并且 `ToolCallbackProvider` 里拿到了 **12 个**工具：

```
maps_geo                  maps_regeocode            maps_around_search
maps_text_search          maps_search_detail        maps_distance
maps_weather              maps_ip_location          maps_direction_driving
maps_direction_walking    maps_direction_transit_integrated      maps_bicycling
```

这 12 个方法**在项目里一行代码都没有**——全是启动时从对方进程问回来的。这就是 MCP 和本地 `@Tool` 的本质区别。

#### 踩到的第二个坑：提示词会把工具"锁死"

接上之后才发现真正难缠的问题：**MCP 明明通了、12 个工具也确实发给了模型，但模型一次都不调。**

原因在系统提示词的「边界」那条：

> 只讨论情感、人际关系相关的话题，其他话题礼貌说明并引导回来

问"杭州明天天气怎么样"属于"其他话题"，模型就规规矩矩把人往情感话题上引，压根走不到调工具那一步。
它的回复甚至说漏了嘴——「如果是查地图信息，也可以直接告诉我要查什么，我来帮你看看」，
**它知道自己能查，只是被提示词拦着。**

修法是在「边界」里加一条例外（`prompts.SYSTEM`）：

> - 例外：约会要用到的**事实信息**（天气、路线、地点、附近有什么菜）算情感话题的一部分。
>   你有查这些的工具就直接查了再说，别让用户"自己去查一下"

改完同一句话，模型从"这属于其他话题"变成"告诉我具体日期，我马上帮你查天气"。

> **这是这一节最值得记的一点：工具接得对，不等于模型会用。**
> 系统提示词和工具是两套独立的指令，**它们会打架**。排查顺序是：
> ① 工具到底发出去没有 → ② 模型愿不愿意调（去翻提示词有没有和它冲突）。
> 第 ① 步可以用一个假的 `ChatModel` 把请求截下来验证——本项目就是这么排除掉"接线问题"的。

## Redis 数据结构

| Key | 类型 | 内容 | TTL |
|---|---|---|---|
| `chat:memory:{chatId}` | String | 消息列表的 Kryo 二进制 | 7 天，每次写入续期 |
| `chat:sessions` | **ZSet** | member = chatId，score = 最后活跃时间戳 | **永不过期** |
| `chat:modes:{chatId}` | **List** | 每轮用的模式（chat / stream / rag / search / mcp / report），按时间顺序 | 7 天，和记忆同步续期 |

**为什么名单用 ZSet 而不是普通 Set**：ZSet 每个成员带一个分数，按分数倒序取出来天然就是"最近聊过的排前面"，而且**顺手把前端要的时间也带回来了**。一个结构解决三件事。

**为什么模式用 List 而不是也上 ZSet**：需求不同。名单要排序 + 去重（同一个会话反复出现只留一条）；
模式是"按轮往后追加、允许重复、只关心顺序"，`RPUSH` + `LTRIM` 两个命令正好就是"追加 + 只留最近若干轮"。

**一个副作用**：消息有 7 天 TTL，但名单里的成员不会过期。所以 `listSessions()` 里加了判断——消息读出来是空的就顺手从名单里剔掉，避免列表上挂着一堆点进去空白的会话。

配置项在 `application.yaml` 的 `ai-agent.chat-memory` 下：

```yaml
ai-agent:
  chat-memory:
    key-prefix: "chat:memory:"
    max-messages: 20    # 每个会话最多留多少条
    ttl: 7d
```
